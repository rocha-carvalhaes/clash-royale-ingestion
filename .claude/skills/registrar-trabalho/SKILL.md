# Registrar trabalho no GitHub Issues

O backlog deste projeto vive em https://github.com/rocha-carvalhaes/clash-royale-ingestion/issues. O agente é o responsável por mantê-lo atualizado. Trabalho sem issue não existe para o projeto.

## Ferramentas

Use as ferramentas `mcp__github__*` (carregue com ToolSearch se necessário): `list_issues`, `issue_read`, `issue_write`, `add_issue_comment`, `sub_issue_write`.
Dono e repositório: `rocha-carvalhaes` / `clash-royale-ingestion`.
Sem as ferramentas MCP, use `gh issue ...` se estiver autenticado. Se nenhum dos dois funcionar, **avise o usuário na resposta final** com o texto pronto da issue. Nunca pule o registro em silêncio.

## Classificação

Tipo (campo nativo `type` da issue):

| Tipo | Quando |
|---|---|
| `Feature` | funcionalidade nova ou evolução do que o pipeline faz |
| `Bug` | comportamento errado, falha de execução, dado incorreto |
| `Task` | manutenção, infra, dependências, documentação, refatoração, investigação |

Labels (só use as que existem; a combinação com `type` já diz o resto):
- Área, uma ou mais: `area:ingestion`, `area:sql`, `area:monitoring`, `area:costs`, `area:infra`.
- `data`: a mudança altera schema, views ou dados já gravados (exige cuidado de migração).

## Fluxo

1. **Antes de começar** qualquer trabalho novo, busque issue parecida com `list_issues` (estado aberto, palavras-chave do título). Se existir, use-a e comente nela; não duplique.
2. **Se não existir, crie** com `issue_write` (`method: create`): título curto no imperativo em português, `type`, labels e corpo com **Contexto**, **Critério de pronto** (checklist) e, se couber, **Impacto** (dados, schema, custo, cron).
3. **Problema encontrado no meio de outra tarefa**: abra issue separada. Se for parte de um trabalho maior, vincule como sub-issue (`sub_issue_write`, que exige o `id` da issue, não o número).
4. **Ao commitar**, cite a issue na mensagem: `Refs #n` no corpo. Quando o commit conclui a issue, use `Closes #n` apenas se o commit chega à branch padrão; em branch de sessão, feche manualmente (passo 5).
5. **Ao concluir**: comente o resultado (o que mudou, arquivos principais, impacto em dados ou schema, como validar) e feche com `state: closed` e `state_reason: completed`. Marque os itens do checklist no corpo. Trabalho abandonado fecha como `not_planned`; duplicada, como `duplicate` com `duplicate_of`.
6. **Na resposta final ao usuário**, diga em uma linha quais issues foram criadas, comentadas ou fechadas, com o número.

## Regras

- Idioma: português, como no resto do projeto. Identificadores de código em inglês.
- Nunca coloque segredos nas issues: token da API, DSN do Neon, URL de ping do Healthchecks, senha de papéis do banco.
- Todo comentário ou corpo de issue escrito pelo agente termina com:
  `---` e `_Generated by [Claude Code](https://claude.ai/code)_`
- Não feche issue de outra pessoa nem reabra issue fechada sem pedido; abra uma nova referenciando a antiga.
- Mudança trivial (typo, formatação) não precisa de issue própria; cite-a no comentário da issue relacionada, se houver.
- Ao final de uma sessão com trabalho pendente, deixe a issue aberta com um comentário de estado (o que foi feito, o que falta) para a próxima sessão retomar sem depender de contexto de conversa.
